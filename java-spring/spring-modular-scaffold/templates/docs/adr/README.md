# 架构决策记录

一决策一文件，**append-only**：推翻旧决策靠新增一条并把旧条标 `Superseded by ADR-NNNN`，不删不改。

## 格式

Nygard 五段 + 一行可执行验证：

```
# ADR-NNNN: 标题
Status: Accepted (YYYY-MM-DD)
Context: 什么处境下要做这个决定
Decision: 决定是什么
Consequences: MUST / MUST NOT 清单，以及代价
Verify: 一条能跑的命令，用来检查这条决策还成不成立
```

`Verify:` 行是 ADR 比普通文档值钱的地方——它把散文变成可校验的东西。三个月后想确认某条决策是否还成立，跑一下就知道，不必读代码猜。

## 这里的条目从哪来

初始几条由脚手架生成，对应生成出来的结构。两件事要知道：

**① 日期是原始决策日期，不是你的项目的生成日期。** 它们记录的是这些决定**最初**在参考实现里被做出的时间。改成生成日期会谎称你的团队在那天讨论过——那正好破坏 ADR 的价值。若你正式复议并确认了某条，再把日期改成复议日期。

**② 它们记录的是架构决策，不是业务决策。** 凡是涉及你的业务模型的（最典型的是 token 里放什么 claim），**必须按自己的情况重写**。照抄业务决策会得到一份看起来像判例、实际上没人做过的记录，比没有记录更误导。

## 新决策怎么加

编号顺延，格式照上。判断标准：**这个决定将来会不会有人质疑？** 会，就写一条。不会的（比如"用 UTF-8 编码"），不用写。

ADR 不是文档义务，是给未来的自己和 agent 的判例——防止同一个问题被反复重新论证，或者被无意中推翻。
