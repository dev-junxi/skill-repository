# 模块验收测试

把模块的产品要求转成可运行、可判定、可追溯、可清理的业务用例。复用“用例目录—执行上下文—证据—资源清单—报告”的职责划分，不把参考模块的客户端、端口、指标或包名复制成通用要求。

## 先确定目标和边界

1. 从用户指定的模块定位仓库，读取适用的 `AGENTS.md`、模块说明、现有接口和测试。用户只给报告时，先追到生成它的用例源码，保留旧报告。
2. 确认被测边界：公共 API、稳定客户端、应用服务或模块对外端口。选一种能覆盖真实业务链路的入口；验收动作和清理都走这一入口，不绕过它直接改数据库来制造通过。
3. 明确要做的是用例方案、离线框架验证、隔离集成测试还是真实服务验收。现有代码和会话已说明的信息直接采用，只询问会改变执行范围的缺失项。
4. 确认写入目标、数据归属、清理办法及可能的实际费用。用户已授权的真实服务测试可继续执行；只要求方案或 skill 时不启动真实服务测试。支付、推送、发信、删除已有业务数据等动作不能从“写测试”推导授权；用沙箱或替身覆盖。

先给出简短影响范围：改哪些文件、复用什么客户端、用哪些测试验证、是否会访问真实环境。项目已有执行器就扩展它，不另建重复框架。Java/Maven 项目按需读 [Java 落地参考](references/java-maven.md)。

## 设计业务用例

用 [验收计划模板](assets/acceptance-plan.md) 组织目录，不强制固定数量。优先级按目标模块的重要性分配；P0通常覆盖必需能力和权限/数据生命周期，P1覆盖组合场景，P2覆盖性能、稳定性等补充维度，不能把该模块的关键能力机械放到低优先级。

每例包含：稳定ID、优先级、场景、合成输入与前置条件、操作序列、可验证预期、禁止结果、证据来源、测试资源和清理步骤。预期在运行前确定，明确正向、反向、边界、重复提交和失败恢复中哪些适用。

- 从用户能命名的能力出发。例如“重复提交不重复扣费”，而非只断言内部函数被调用。
- 确定性契约用精确断言；业务状态检查真实读取结果，不能用请求成功替代持久化成功。
- 权限隔离、删除和过滤先做正命中：先证明目标数据存在且可由正确身份/作用域读取，再检查错误身份不可读或删除后消失。空结果本身不是成功证据。
- 对列表、分页、详情、来源/关联字段和异步结果分别明确检查范围。一个端点通过不能代表所有读路径通过。
- 开放语义或LLM行为依目标项目约定使用真实模型/独立评审，或标为REVIEW；Mockito的固定回答只验证编排。非空文本、固定关键词、单个排序分数不能证明语义正确。
- 模块不支持的业务能力保留缺口；不要在客户端过滤、隐藏响应字段、向问题注入正确答案或放宽预期来掩盖服务失败。

## 实现执行、证据和清理

采用 [执行与结果契约](references/execution-contract.md)。可以沿用现有命名，但职责要可分离：

| 职责 | 内容 |
|---|---|
| Case / Samples | 用例描述、稳定ID、优先级和动作 |
| Context | 经公共入口执行业务动作、断言、轮询和证据引用 |
| Runner | 计划选择、逐例状态、故障策略、最终清理 |
| Evidence | 脱敏调用记录、耗时、真实响应、异常分类 |
| Resources | 本轮创建资源的持久化归属清单、恢复清理 |
| Reports / Config | 六列表报告、总体指标、运行配置和退出规则 |

核心执行约束：

- 一例断言或解析失败不吞掉其他独立用例。确有环境不可用时停止相关调用，把剩余选中项明确记为SKIP，仍写报告并清理。
- 区分预期业务拒绝、契约失败、解析失败、传输失败。401/403可能正是权限反例的预期，不能一概判为环境失效；没有HTTP状态也不能自动判为断网。
- 为异步任务定义终态、等待上限和失败传播；只重试有幂等性依据的操作。业务失败不通过反复重跑刷成PASS。
- 使用run_id及可核验的资源归属。创建前记录意图，收到回执再记录实际ID和状态；失败回执不代表资源没创建。清理只触及本轮资源，不遍历删除全部业务数据。
- 正常结束、断言失败和异常都进入finally清理。验证删除后的业务可见状态；清理失败独立记录并阻塞“全部通过”结论。提供按原清单恢复清理的入口，校验环境和归属，不承诺强制杀进程后一定已清理。
- 记录合成数据的请求响应、实际检查和清理过程。密钥、鉴权头、凭证URL、支付令牌和真实个人数据不进入日志；异常正文也须脱敏。此测试证据不等于允许在生产业务代码打印请求响应。

## 提供可重复运行入口和报告

按 [使用说明模板](assets/acceptance-readme.md) 提供一键入口，接入项目已有构建工具，区分离线验证、真实验收、按优先级执行和恢复清理。普通单元测试默认不访问真实服务；已有项目规则优先，不硬编码参考机器的JDK路径或服务地址。

每轮写入独立运行目录，目录随构建工具调整，常见布局：

```text
acceptance/<run_id>/
  run.json                 # 环境/版本/选中用例/参数，不能含凭证
  P0-report.md             # 只为选中的优先级生成
  summary.md
  results.json
  evidence/<case_id>.jsonl
  resources.json           # 若用例创建外部资源
  cleanup-result.json      # 若执行恢复清理
```

六列表：`用例ID | 场景与输入 | 预期结果 | 实际结果与证据 | 结果 | 耗时(ms)`。实际结果链接到证据；JSON保存逐项断言。Markdown转义竖线和换行；按项目规则给手写文档及受检查的生成文档添加front matter。

每例完成即持久化结果，按组及最终结束刷新总体报告。异常中断也应保留已完成结果、未执行项和清理状态。报告区分完整目录、选中计划和实际执行数，筛选P0不能宣称全部验收通过。

指标跟模块要求绑定：始终报告状态分布、覆盖分母和清理结果；适用时再增加业务正确率、隔离失败、生命周期残留、完成可见延迟、性能和成本。未测写“未验证”，未采集用量写“未返回”；不能写成零风险、零成本。小样本串行P95需注明样本量和算法，不推断并发容量；没有SLA不宣称性能达标。

## 验证和复测

先离线验证测试设施，再按授权范围做真实验收：

- 验证失败后下一例仍执行、解析错误不误判为断网、预期拒绝不触发全局跳过、异步失败能终止等待。
- 验证创建回执丢失、清理失败、清单归属不符、分页空页/重复页和报告转义等实际存在的脆弱路径。按适用性选择，不为凑数量添加测试。
- 验证报告统计与结果一致；无断言或仅空依据不能成为PASS；只运行一部分不能给整体“全部通过”。
- 修复用例时先用现有失败或回归测试确认问题，区分业务缺陷、客户端DTO缺陷、执行器缺陷和预期错误。修正输入契约后保留原业务断言；真正改变验收标准时明确说明原因。
- 保留旧报告，用新run_id复测受影响用例。离线测试通过不更新旧真实验收状态。测试框架修复只证明框架行为，真实业务结果需真实证据。
- 运行目标仓库要求的格式化、文档/架构卡口和与改动相称的测试；不要通过修改规则来消除失败。

输出：用例与入口路径、执行命令、离线和真实运行各自的结果、报告路径、残留资源、失败原因及未验证范围。用户能据此复跑和判断下一步。

需要迁移现成Java目录、查看这次记忆模块的失败经验或套用非记忆业务示例时，读 [参考实现与迁移示例](references/examples-and-lessons.md)。
